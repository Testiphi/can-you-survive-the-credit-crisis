# 04 · 数据源 · 性能 · 单人开发边界

> 本文档回答两个问题：
> 1. **建一个模拟盘，性能要求高不高？**
> 2. **在个人开发条件下，能做到什么样？**

## 第一部分 · 数据源

## 1.1 完全免费、可直接使用

| 数据 | 来源 | 用途 |

## 1.2 收费 / 需替代方案

| 拿不到的 | 原因 | 替代方案 |
|---|---|---|
| 单名 CDS 日频历史 | Markit / IHS 收费 | `BAMLH0A0HYM2` × 公司 β 映射（**做机制，不还原数据**） |
| ABX.HE 指数 | Markit 收费 | 用房价指数 + 高收益利差合成；学术论文附录里有部分公开序列 |
| 单股期权历史隐含波动率 | ORATS / OptionMetrics 收费 | BS + VIX 联动的参数化曲面合成 |
| 已退市股票的精准历史股价（LEH/BSC/WM/WB） | 免费源覆盖不全 | 板块指数 + 行业映射合成，并校准关键跌幅（如 LEH 从 $60 → $0） |
| 真实 tick 数据 / 订单簿 | 极其昂贵 | **不需要**。回合制日频用不上 |

## 1.3 必须接受的定位

> **这是一个"基于历史机制的高保真模拟"，不是"历史录像回放"。**

这句话要早点确立。否则会永远卡在"数据不够真实"的泥潭里——而那个泥潭没有底。

一旦接受合成，反而多了一个好处：**可以生成平行时间线**（见 [02 §7.3](02-系统架构与数据结构.md)），这是还原派做法永远做不到的重玩性来源。

## 1.4 数据管道

```
data/pipeline/*.py
  fetch_fred.py       → 拉 FRED 序列
  fetch_equity.py     → 拉指数与个股日线（yfinance / stooq）
  synth_equity.py     → 为退市个股合成路径并校准关键节点
  synth_options.py    → 由 VIX 合成 IV 曲面与期权链
  synth_credit.py     → 由高收益利差合成单名 CDS
  build_events.py     → 手工整理的事件卡 → JSON
  export.py           → 输出前端直接消费的静态 JSON
```

**产出物：** `data/processed/*.json`，一次性生成，**运行时零网络请求**。

**体积估算：**

```
522 个交易日 × 40 个标的 × ~10 个字段 ≈ 208,800 个数字
≈ 500 KB JSON，gzip 后 < 100 KB
```

**整个数据集可以一次性载入内存。不需要数据库，不需要后端，不需要索引。**

## 第二部分 · 性能

## 2.1 结论

> **这个品类的性能完全不是瓶颈。一台十年前的笔记本、甚至树莓派都能跑。**

预算目标：**单回合 < 1 ms**。而 60fps 的一帧有 16.7 ms。也就是说一回合的模拟只占一帧的 0.006%。

### 2.2 逐项拆解（单回合）

| 操作 | 规模 | 耗时 |
|---|---|---|
| 价格生成（含跳跃扩散） | 40 个标的 | ~5 μs |
| 事件卡触发判定 | ~120 张卡，DAG 遍历 | ~20 μs |
| NPC 决策 | 200 个 agent × 启发式规则 | ~100 μs |
| 期权重定价 | 600 个合约 × Black-Scholes | ~120 μs |
| 玩家订单成交（含冲击计算） | < 10 笔 | ~5 μs |
| 盯市 + 保证金 + 强平 | 40 个持仓 | ~10 μs |
| 监管评估 | 常数 | ~2 μs |
| **合计** | | **≈ 0.3 ms** |

### 2.3 内存

| 项 | 估算 |
|---|---|
| 历史数据（520 天 × 40 标的） | ~5 MB（反序列化后） |
| 单局运行时状态 | ~10–30 MB |
| 峰值（含图表缓存） | < 50 MB |

### 2.4 前端渲染

- `lightweight-charts` 基于 canvas，**几万根 K 线无压力**。本作只有 520 根。
- 唯一的坑：**不要每帧重绘**。只在状态变化时重绘。K 线图不是实时行情，不需要 60fps。
- React 层面：500 个数字的表格，任何现代框架都是瞬间。不需要虚拟滚动。

## 2.5 三个真正的性能陷阱（提前避开）

### 陷阱一：蒙特卡洛期权定价（**最致命**）

如果为了"更真实"而用蒙特卡洛给期权定价：

```
10,000 条路径 × 600 个合约 × 522 天 = 31 亿次路径步进
→ 分钟到小时级。游戏直接不可玩。
```

**解法：用 Black-Scholes 解析解 + 参数化波动率曲面。** 从毫秒级降到微秒级，精度反而更稳定。**这是整个项目最重要的一个性能决策。**

### 陷阱二：限价订单簿（LOB）撮合

如果你决定做 tick 级撮合模拟，工作量会瞬间膨胀 10 倍（撮合引擎、队列、延迟模型、部分成交撮合），而回合制日频根本用不上。

**解法：不要做。** 用 [03 §6](03-金融模型与数值.md) 的平方根冲击律替代——**它用 10 行代码实现了 LOB 90% 的玩法效果。**

### 陷阱三：批量对局的 GC 压力

交互时每回合几分钟一次，GC 完全不是问题。但 10000 局 × 522 回合 = 522 万回合的批量跑，如果每回合都 `new` 一堆对象，GC 会吃掉大量时间。

**解法**：批量模拟器（`tools/sim`）里复用对象池 / TypedArray。**交互模式不要优化**——那是过早优化。

## 2.6 批量对局的真实成本

```
10,000 局 × 522 回合 × 0.3 ms ≈ 1,566 秒 ≈ 26 分钟（单线程）
```

嗯，比我之前在 README 里写的 4–5 分钟要长。**修正：**

| 方案 | 耗时 |
|---|---|
| 单线程，完整模拟 | ~26 分钟 |
| 8 个 Worker 并行 | ~3.5 分钟 |
| 简化模式（跳过期权重定价，只跑现货策略） | ~3 分钟单线程 |

**结论**：调平衡跑一次 3–5 分钟是可接受的（喝杯咖啡）。**但内存要注意**：不要同时开 10000 局，用 `8 workers × 1 局` 的池子顺序跑。

## 2.7 什么时候性能才会成为问题

只有下面三种情况：

1. 你要做**实时 tick 级 + LOB 撮合**（→ 不要做）
2. 你要做**实时多人对战**（→ 那是后端问题，不是算力问题）
3. 你要做**强化学习训练 AI 对手**（→ 研究项目，不要做）

**除此之外，性能永远不是你的瓶颈。**

## 第三部分 · 单人开发的现实边界

## 3.1 真正的瓶颈：不是算力，是人

| 工作类型 | 占比 | 说明 |
|---|---|---|
| **内容写作** | ~35% | 120+ 张事件卡的叙事、新闻文案、教学提示。**这是最大的工作量，且无法外包给代码生成** |
| **平衡调参** | ~25% | 反复跑蒙特卡洛、看策略机器人分布、改参数 |
| **UI/交互** | ~25% | 图表、下单面板、持仓表、复盘界面 |
| **引擎逻辑** | ~15% | 全部公式和数据结构。**代码量其实不大** |

**很多人会以为引擎是主体。恰恰相反——引擎只有 15%。**

## 3.2 三档现实目标

### Tier A · 约 40–80 小时（2–4 周业余）

**交付**：P0 + P1 核心。K 线、新闻卡、多/空/清仓、日推进、净值曲线、种子存档、铁人模式。

**可行性**：★ ★ ★ ★ ★ **完全可达**。有 TS/React 经验的人可以做到。

**这一档就已经是一个完整、可玩、可分享的小游戏了。**

### Tier B · 约 150–250 小时（2–3 个月业余）

**交付**：D0/D1/D2 完整。保证金、做空、15 合约期权、期货、信用利差机制、流动性冲击、五类 NPC、监管阶梯 L1–L3、动态相关性、复盘界面、蒙特卡洛调平衡工具。

**可行性**：★ ★ ★ ★ **可达，但需要持续投入**。瓶颈是内容（120+ 张事件卡）和平衡，不是技术。

**风险**：这一档最容易烂尾。建议严格按 P1 → P2 分阶段交付，每阶段都能停下。

### Tier C · 6 个月以上

**交付**：D3 完整。投行死亡螺旋、卖保护、对手方风险、场外合约模板、监管 L4–L5、平行时间线、玩家改写历史、排行榜后端。

**可行性**：★ ★ ★ **可达，但需要真正的承诺**。

## 3.3 单人开发者做不到的事（诚实清单）

| 做不到 | 原因 |
|---|---|
| 还原真实历史期权链 | 数据收费，重建是研究项目 |
| 真实 tick 数据 / 订单簿重建 | 数据费用 + 工程量 |
| 用强化学习训练银行 AI | 研究级难度 |
| 实时多人 + 反作弊 | 需要后端团队与运维 |
| 3D / 角色立绘 / 过场动画 | 美术产能；且**对本作是错误的投入方向** |
| 授权真实市场数据做商业发行 | 费用 |

## 3.4 单人开发者反而做得更好的事

| 优势 | 说明 |
|---|---|
| **设计一致性** | 没有委员会、没有多人协作的妥协 |
| **机制诚实** | 没有变现压力逼你把游戏做简单 |
| **迭代速度** | 改个参数、跑 5 分钟模拟、立刻知道结果 |
| **叙事深度** | 一个人写的 120 张事件卡，语气是统一的 |
| **免费分发** | 纯静态前端 → GitHub Pages / Netlify，零成本上线 |

## 3.5 关键范围护栏（Scope Guards）

这六条如果守住，项目能完成；守不住，一定烂尾：

1. **不做 LOB 撮合。**
2. **不做蒙特卡洛期权定价。**
3. **不做完全自由的场外合约**（只给 3 种模板）。
4. **不做实时多人**（用"种子对战"替代，效果 80%，成本 5%）。
5. **不做美术资产**（用终端美学：深色、等宽字体、红绿、数据密度。**这既是正确的观感，也几乎零成本**）。
6. **每一期都必须有可玩版本**，不允许"做到一半才有东西能玩"。

## 3.6 美术方向：终端美学

不要做角色立绘。本作正确的视觉语言是 **Bloomberg 终端 / 数据可视化**：

- 深色背景（`#0a0e14`）、等宽字体、克制的红绿
- 信息密度高、留白少——**这本身就是沉浸感**
- 危机时刻：整个界面泛红、波动加剧、新闻弹窗、数字跳动加速
- 唯一的"美术工作"是排版与动效，成本极低，且气质极对

**恐怖感来自数字和文字，不来自画面。**

## 3.7 分发

```
pnpm build → dist/ 静态文件 → GitHub Pages / Netlify / Cloudflare Pages
```

- 零服务器成本
- 存档用 `localStorage`（铁人模式下每回合自动写）
- 种子对战用 URL 参数：`?seed=42&d=2&id=hedge_fund`
- 分享一个链接就能让别人挑战同一场危机

**这是整个项目里性价比最高的功能：零后端，极强传播力。**
